01 / Comparison

Three restrained harness philosophies.

Pi、DeepSeek Harness 与我的 GGAI / Agent Harness 都在避免把模型周围的软件层做成巨型业务框架，但它们选择的“可插拔边界”并不相同。理解这个差异，比简单比较谁支持更多工具更有意义。

Pi / Minimal coding harness

Small core, multiple resource types.

Pi 把核心 coding loop 保持得很小，主要通过 TypeScript Extensions、Agent Skills、Prompt Templates 与 Packages 扩展。Skills 按需加载，Extensions 可以注册工具、事件、命令和 UI；像 subagent / plan mode 这类能力并不默认塞进核心。

  • 扩展单位：Extension / Skill / Prompt / Package
  • Skill 强调 progressive disclosure
  • 核心保持少机制、强可定制
  • 用户可以组合自己真正需要的能力
DeepSeek Harness / Cordis

Everything is a plugin.

DeepSeek Harness 把插件边界推进得更彻底：模型适配器、Session、System Prompt、Tool Registry、Agent Loop 等都以 Cordis plugin / service / typed event 组合。配置可以替换底层能力，Session 以 append-only event log 作为运行事实来源。

  • 扩展单位：Cordis Plugin / Service / Typed Event
  • Tool pipeline 有明确 pre / execute / post / result seam
  • Agent loop 本身也可替换
  • Trace / Session 是一等运行数据
My direction / GGAI Harness

Stable runtime, heterogeneous capability protocols.

我的实践更偏向保留一个稳定的 Single-Agent Runtime，让不同能力使用最适合自己的协议接入：Skill 负责知识与流程披露，MCP 负责外部 Tool Contract，Workflow 承担状态化业务过程，SubAgent 负责隔离执行。

  • 扩展单位：Capability Contract
  • 不要求 Skill / MCP / Workflow 统一成同一种插件
  • Runtime 不承载领域业务逻辑
  • Decision Context 与 Execution Context 明确隔离

02 / Plugin Boundary

“Pluggable” means different things.

Pi 更像“在一个最小 coding harness 周围加载不同资源”；DeepSeek 更像“所有运行组件都通过统一插件 / event / service 模型组合”；我的方向则更强调领域能力协议本身的差异，不把所有东西为了统一而统一。

03 / Thesis

Stable spine, pluggable perimeter.

我的 Harness 研究重点不是追求“所有东西都可替换”，也不是把 Runtime 做成一个功能全集，而是寻找最小但稳定的控制脊柱：模型每一轮需要什么上下文、如何选择能力、如何执行、失败如何被结构化、完整 Trace 如何留在 Prompt 之外。

A / Runtime

Keep the decision loop generic

Runtime 负责 Turn / Step、状态、上下文、能力选择与恢复边界；领域 Planner / Executor 不应成为通用 Runtime 的硬编码节点。

B / Capability

Use the right protocol for the job

Skill 适合渐进披露知识和流程；MCP 适合外部工具服务；Workflow 适合有状态的确定 / 半确定过程；SubAgent 适合隔离且独立的执行。

C / Context

Decision context ≠ execution context

模型下一次决策只消费必要 Observation / Summary；完整工具输出、Worker transcript 和 Artifact 细节保留在执行边界与 Trace。

D / Evidence

Trace is system evidence

Trace 不是为了日志好看，而是用于恢复、评测、问题分类与工程闭环，并与长期 Memory / Experience 形成连接。

04 / Patterns

Patterns carried across Navigation, GIS and GGAI.

  • 01

    Runtime ≠ Domain Logic

    通用运行时负责 Agent loop、状态与控制；领域行为通过 Skill / MCP / Workflow 等能力挂载，避免业务过程不断进入 Runtime。

  • 02

    Tool Error ≠ String

    工具失败不只返回一段文本，而是形成可被 Runtime 与 Agent 消费的分类、recovery metadata、Artifact 状态和后续动作信息。

  • 03

    Progressive Capability Exposure

    模型不必一直看到全部能力。按任务与阶段暴露 Skill / Tool，减少工具过载、错误选择和不必要的上下文成本。

  • 04

    Decision Context ≠ Execution Context

    系统侧可以保留完整 execution evidence，但模型决策侧只读取最小充分信息，避免长期运行中的上下文污染。

  • 05

    SubAgent is an Execution Strategy

    SubAgent 不是“系统高级”的象征；只有独立、可隔离的任务才值得 fan-out，共享外部状态的任务优先 direct execution。

  • 06

    Evaluate the Trace, not only the Answer

    任务完成、工具选择、参数、恢复、Artifact 与最终回复共同组成可靠性；最终文字答案只是 Agent 轨迹的最后一层表现。

05 / Design Trade-off

What I borrow—and what I keep different.

Pi 给我的启发是核心越小，外围越应该有清晰的扩展资源；DeepSeek Harness 给我的启发是运行时扩展点、typed tool pipeline、append-only session / trajectory 应该成为一等架构对象。我的业务场景又要求 Skill、MCP、Workflow 和 SubAgent 保留各自的语义，所以当前更倾向“统一 Runtime 语义，不统一所有能力协议”。

From PiMinimal core · progressive disclosure · user-owned extensibility.
From DeepSeekExplicit seams · typed execution pipeline · trace as durable system data.
Keep differentCapability protocols remain heterogeneous when their semantics differ.
Optimize forDomain isolation · context cleanliness · failure recovery · observability.
AvoidTurning the general Runtime into a universal workflow engine.
Next questionHow much of Memory / Eval should itself become pluggable without weakening the stable spine?
Research direction

我想做的不是一个“能力最多”的 Harness，而是一个模型更换、领域扩展和 Workflow 增长之后，仍然保持边界清楚、上下文克制、Trace 可解释的软件层。
