01 / Overview

From domain agents to a general runtime.

GGAI 的目标不是继续增加一个新的领域 Agent，而是把此前 Navigation Agent、GIS Agent 中反复出现的运行、工具、上下文与评测问题抽象成通用基础设施。Runtime 保持业务无关，领域能力通过 Skill 与 MCP 按需挂载；主 Agent 还可以把不同业务状态的 Sub Agent 当作工具进行派发与组合。

02 / Contribution

Designing the harness around the model.

  • 01

    Runtime 架构重构

    将系统从领域 Agent 调整为通用 Agent Runtime，把领域能力下沉到 Skill 与 MCP，避免通用运行时被业务逻辑污染，并为后续扩展建立稳定边界。

  • 02

    QueryEngine / Context Engineering

    参与设计消息构造、系统提示拼装、历史消息、Skill/MCP 状态、Memory 与压缩上下文管理，让模型在长链路执行中获得可控、可追踪的上下文。

  • 03

    Tool Orchestrator

    统一本地工具与 MCP 工具调用，支持参数 schema 校验、工具执行、失败识别与 recovery metadata 生成，让工具层具备一致的执行与恢复语义。

  • 04

    Skill / MCP 可插拔体系

    支持用户手动启用 local-route、openstreet、qgis、workspace 等自定义 Skill/MCP，在保持领域隔离的同时控制工具可见性与能力边界。

  • 05

    Trace-level Eval

    基于用户短期记忆 Session 构建 Agent 轨迹评估 Skill，评测任务成功、工具选择、参数合法性、恢复和最终答案完整性，而不是只看最终回复。

  • 06

    Eval 驱动迭代

    通过 LLM-as-Judge 发现并修复工具失败误判、低级工具调用过多、schema 缺字段、Skill loop、领域工具误触发等问题，并据此持续迭代领域知识与工作流。

03 / Evaluation

Evaluate the trajectory, not only the answer.

GGAI 将评测对象从“最终回答好不好”扩展到完整 Agent Trace。这样可以区分答案问题、工具选择问题、参数问题与恢复问题，并把错误定位到具体运行环节。

Task success rate任务是否真正完成。
Tool correctness工具选择与调用是否正确。
Tool call F1工具调用行为的精确度与召回。
Parameter validity工具参数是否满足 schema 与业务约束。
Recovery success失败后能否识别原因并恢复。
Answer completeness最终答案是否覆盖任务要求。
Core idea

通用 Agent 的可靠性不只来自更强的模型，也来自 Runtime 边界、工具合约、上下文管理、可观测 Trace 与可重复的评测闭环。
