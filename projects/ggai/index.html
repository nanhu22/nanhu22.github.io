01 / Architecture

Generalize the runtime, not the business logic.

GIS Agent 用显式 Multi-Agent 角色解决了复杂 Workflow，但也带来新的架构问题：如果每增加一个领域就复制 Planner / Executor / Orchestrator，通用 Runtime 会重新被业务流程污染。GGAI 的核心改动是把“如何完成某个领域过程”更多沉入 Skill、MCP、Tool 与 Workflow，让主 Runtime 只保留通用的决策、状态、能力选择、上下文与运行控制。

02 / Context Model

Decision context ≠ execution context.

这是 GGAI 相比前两代最重要的运行时边界之一。Main Agent 需要知道的是当前目标、必要历史、启用能力、关键 Observation 与结果摘要；它不需要长期持有某次 QGIS processing 的所有原始输出，也不应该把多个 SubAgent 的完整 transcript 全量回灌到主上下文。

A / Decision Context

Main Agent sees less

任务目标、约束、历史摘要、Memory、Skill/MCP 状态、关键 Observation 和当前决策所需证据。

B / Execution Context

Workers keep detail

具体工具参数、中间 Artifact、SubAgent 工作记忆和执行 Trace 被保留在工具 / Worker 边界。

C / Return Boundary

Observation over transcript

执行完成后优先返回结构化 Observation、Artifact 引用与摘要，而不是无限增长的完整运行文本。

D / Trace Store

Keep evidence outside prompt

完整执行证据仍然被 Trace 系统记录，用于调试、评测和恢复，但不等于模型下一轮必须读取全部历史。

Design principle

Context Engineering 的目标不是“尽量塞更多上下文”，而是让模型在每一次决策时只看到最有用的信息，同时让完整执行证据在系统侧保持可追踪。

03 / Representative Cases

One runtime, three execution shapes.

从脱敏 Trace 可以看到，GGAI 的“通用”不来自把所有任务强行放进同一种流程，而是让同一个 Runtime 根据任务结构选择不同执行形态。

A

Parallel route comparison

多个独立目的地没有共享写状态。Main Agent 激活路线能力、拆分目的地、批量启动 SubAgent，收集输出后统一比较与推荐。

PDF case · independent branches → fan-out.
B

Direct sequential QGIS workflow

统计 POI、计算指标、写字段、样式化和保存文件会连续修改同一个 GIS project / layer state，因此保持 Main Agent direct execution。

Shared mutable state → no unnecessary SubAgent split.
C

Trace-level business benchmark

真实 GIS 任务通过同一个生产 Runtime 执行，Trace / Artifact 被收集并用于任务成功、工具正确性、恢复与输出有效性评估。

Execution evidence closes the engineering loop.
04 / Harness

A restrained harness around a general agent.

GGAI 的 Harness 不把领域 Workflow 硬编码在 Runtime：QueryEngine / Context 层组织决策输入；Skill/MCP 决定能力可见性；Tool Orchestrator 统一工具执行、schema 与失败语义；Memory 管理长期信息；SubAgent 作为工具扩展并行执行；Trace Eval 在 Prompt 之外保留完整行为证据。

05 / Contribution

Designing the harness around the model.

  • 01

    Runtime 架构重构

    从领域 Agent 体系收敛为通用 Single-Agent Runtime，把领域过程与能力下沉到 Skill、MCP、Tool 和 Workflow，避免 Runtime 被业务逻辑污染。

  • 02

    QueryEngine / Context Engineering

    参与消息构造、系统提示、历史摘要、能力状态、Memory 与压缩上下文管理，明确区分主 Agent 决策上下文与执行侧详细 Trace。

  • 03

    Tool Orchestrator

    统一本地工具与 MCP 调用，支持参数 schema 校验、工具执行、失败识别与 recovery metadata，让执行层拥有一致的工具语义。

  • 04

    Skill / MCP 可插拔体系

    支持按需启用 local-route、openstreet、qgis、workspace 等领域能力，提升能力隔离、工具可控性与 Runtime 可复用性。

  • 05

    Selective SubAgent as Tool

    只在任务独立、状态可隔离时派发 SubAgent；共享状态工作流保持 direct-main execution。SubAgent 输出通过摘要 / Observation 边界回流主 Agent。

  • 06

    Trace-level Eval

    基于完整 Agent Trace 评估任务成功、工具选择、参数合法性、恢复与最终输出，并把失败分类为可修复的 Runtime / Tool / Context 问题。

06 / Evaluation

Close the loop with a real GIS benchmark.

GGAI 的 GIS benchmark 让任务真正穿过生产 Runtime、真实工具、Artifact 与 Trace，而不是只对最终文本打分。当前经过有效业务输入验证的任务完成率保持稳定；缺失输入路径、外部环境未准备等 setup 问题被单独归类，不与 Agent 在有效业务条件下的能力混为一个指标。

Engineering takeaway

第三代架构的核心不是“用了更多 Agent”，而是把通用 Runtime、领域能力、执行上下文、长期 Memory 和完整 Trace 分开管理，从而让系统既能扩展业务，又能控制复杂度。
